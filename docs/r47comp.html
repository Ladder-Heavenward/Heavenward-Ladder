Can a Program’s Type Say What It Does?

Can a program’s type say what it does? A programmer writes, before any code, what kind of thing goes in and what kind comes out: a list of names in, a number out; a pair in, one of its parts out. A checker reads those labels and refuses programs whose pieces do not fit. Most of the time a label says little, since many programs take a list of names to a number. But some labels say a great deal. A program that must work for every kind of thing at once, and takes a thing to a thing of the same kind, can do only one thing: hand back what it was given. A program that takes two things of any one kind to one of them can only pick the first or the second. What makes this hard to believe is that nothing about the code is read, only its label. This page reads types as the things of a category and programs as its arrows, and finds that the rung’s arrows explain the labels: pairs and choices are products and sums, the technique that turns a program of two inputs into one of one input is 47f’s adjunction, a container that can be mapped over is a map of categories, and a program for every type is a natural map, fixed by its arrows in the way 47g fixed a thing. A database is read the same way, with a join as a limit.

A type is a thing and a program that always stops is an arrow, and running programs one after another is running arrows in a row. Pairs of types are products and tagged choices are sums, so the counts of members multiply and add, and a program of two inputs is a program that hands back a program. Lists, with the technique that applies a program to each entry, form a map of categories. A program written for every type without looking at the type is a natural map, and the arrows it must be carried along by leave it almost no room: one program for a thing to a thing, two for a pair to a thing. A table of a database is a set of rows, a column that names a row of another table is an arrow, and the join of two tables over a third is the limit of their two arrows.

47·comp.1Types as Things, Programs as Arrows

A typed language has types: Bool, with the two members true and false; Int, the whole numbers; String, the rows of letters; One, with a single member ⋆; and the types built from them. A program from X to Y that has no other effect and always stops takes each member of X to one member of Y, so it is a function. Running one program on the output of another is running functions in a row, and the program that hands back its input does nothing.

Types-and-programs technique: the types of a language, with its stopping programs read as functions, form a category, so every technique of this rung made with arrows alone holds of programs. Proof: running in a row is 9b’s composing of functions, where brackets do not matter, and the do-nothing program is the identity function; those are 47a’s techniques. Held in trust: that the programs all stop, as on 47j.

\mathrm{len} : \mathrm{String} \to \mathrm{Int},\ \ \mathrm{even} : \mathrm{Int} \to \mathrm{Bool} @@ two programs, two arrows
(\mathrm{even} \circ \mathrm{len})(\text{“arrow”}) = \mathrm{even}(5) = \text{false} @@ run in a row: the types fit, so the checker allows it
\mathrm{len} \circ \mathrm{even} \text{ is refused} @@ even ends at Bool, and len starts at String
\htmlClass{new}{\mathrm{Bool} \to \mathrm{Bool} \text{ has } 2^2 = 4 \text{ programs: keep, flip, always true, always false}} \quad \blacksquare @@ two outputs for each of two inputs

So a checker that refuses len ∘ even is refusing an arrow that starts where the last one did not end, 47a4’s refusal, and the count says that a type of four programs leaves the label a lot to say and the code a little.

47·comp.2Pairs, Choices and Programs That Hand Back Programs

The pair type X × Y holds pairs (x, y), and a program into it is a pair of programs, one for each part: 47d’s pair-map technique, so X × Y is the product. The choice type X + Y holds members tagged left x or right y, and a program out of it is a pair of programs, one for each tag: 47d’s cases-map technique, so X + Y is the sum. The function type Y → Z holds programs, and 47f’s pair-to-function technique matches programs X × Y → Z with programs X → (Y → Z), which take the first input and hand back a program waiting for the second.

Type-counts technique: for types with finitely many members, X × Y has |X|·|Y| members, X + Y has |X| + |Y|, and Y → Z has |Z| to the power |Y|; and the matchings of the pair-map, cases-map and pair-to-function techniques give |Z|^{|X|·|Y|} = (|Z|^{|Y|})^{|X|} and |Z|^{|X| + |Y|} = |Z|^{|X|}·|Z|^{|Y|}. Proof: rung 4’s counting of pairs, of a set split in two, and of choices made once for each input; matched sets have equal counts.

|\mathrm{Bool} + \mathrm{Three}| = 2 + 3 = 5 @@ the type-counts technique, sums; Three has three members
|(\mathrm{Bool} + \mathrm{Three}) \to \mathrm{Bool}| = 2^5 = 32 @@ the type-counts technique, functions
|\mathrm{Bool} \to \mathrm{Bool}| \cdot |\mathrm{Three} \to \mathrm{Bool}| = 4 \cdot 8 = 32 @@ the type-counts technique, pairs of programs
\htmlClass{new}{(X + Y) \to Z \ \cong\ (X \to Z) \times (Y \to Z)} \quad \blacksquare @@ the cases-map technique: a program out of a choice is a program for each tag

So the counts of types obey the techniques of powers, and the techniques of powers are the rung’s universal properties counted. A technique of programming, “a program out of a choice handles each case”, is a statement of arrows.

47·comp.3Map Over a Container

For each type X, List X holds the finite rows [x₁, …, xₙ] of members of X. For each program f : X → Y, map f : List X → List Y applies f to each entry and keeps the order: map f [x₁, …, xₙ] = [f(x₁), …, f(xₙ)]. Option X holds either nothing or one member of X, and map f leaves nothing alone and applies f to the member.

Map-over technique: List, sending X to List X and f to map f, is a map of categories from types to types, and so is Option. Proof: entry by entry, map of the do-nothing program leaves each entry as it is, and map (g ∘ f) puts g(f(xᵢ)) in place i, which is what map g does after map f; the length and the order are kept. Option is the case of rows of length at most one.

f(n) = n + 1,\ \ g(n) = 2n,\ \ \text{on } [1, 2, 3] @@ two programs Int → Int, and a row
\mathrm{map}\, f\, [1, 2, 3] = [2, 3, 4],\ \ \mathrm{map}\, g\, [2, 3, 4] = [4, 6, 8] @@ map f, then map g
\mathrm{map}\,(g \circ f)\, [1, 2, 3] = [g(2), g(3), g(4)] = [4, 6, 8] @@ map of the row run
\htmlClass{new}{\mathrm{map}\,(g \circ f) = \mathrm{map}\, g \circ \mathrm{map}\, f} \quad \blacksquare @@ the map-over technique

So 47b’s matched-to-matched technique applies: matched types have matched list types. Programmers rely on the second technique when they fuse two passes over a list into one, and the map-over technique is why the fused program gives the same answer.

47·comp.4A Program for Every Type

Some programs are written once for every type: reverse, which turns a row round at each type X; the do-nothing program; the program that swaps a pair. Such a program is a family p_X, one at each type, written without looking at what X is. Held in trust: a program written for every type without looking at the type is carried along by every program f : X → Y, so it is a natural map in 47c’s sense. For reverse, the square reads reverse ∘ map f = map f ∘ reverse.

Only-identity technique: a family p_X : X → X carried along by every program is the do-nothing program at every type. Proof: take x in X and f : One → X with f(⋆) = x. One has one member, so p_One(⋆) = ⋆. The square for f gives p_X(x) = p_X(f(⋆)) = f(p_One(⋆)) = f(⋆) = x. This is 47g’s arrows-into technique in small: the family is fixed by what it does to one member of one type.

f(n) = 2n,\ \ \text{on } [1, 2, 3] @@ a program and a row
\mathrm{reverse}(\mathrm{map}\, f\, [1, 2, 3]) = \mathrm{reverse}\, [2, 4, 6] = [6, 4, 2] @@ map, then reverse
\mathrm{map}\, f\, (\mathrm{reverse}\, [1, 2, 3]) = \mathrm{map}\, f\, [3, 2, 1] = [6, 4, 2] @@ reverse, then map
\htmlClass{new}{\mathrm{reverse} \circ \mathrm{map}\, f = \mathrm{map}\, f \circ \mathrm{reverse}} \quad \blacksquare @@ the square closes on this row; in general, entry by entry

So the label “for every X, X to X” says what the program does, and the code need not be read. A program that broke the square, by looking at its type and adding 1 when X is Int, is exactly what the held-in-trust statement rules out, and it is not written for every type.

47·comp.5Two Picks

The label “for every X, a pair of X to an X” leaves a little more room. Taking the first part and taking the second part both fit it. The square for f : X → Y reads p_Y(f(x), f(y)) = f(p_X(x, y)).

Two-picks technique: a family p_X : X × X → X carried along by every program is either the first part at every type or the second part at every type. Proof: take (x, y) in X × X and f : Bool → X with f(false) = x and f(true) = y. The square for f gives p_X(x, y) = p_X(f(false), f(true)) = f(p_Bool(false, true)). If p_Bool(false, true) = false, then p_X(x, y) = x for every X, x and y; if it is true, p_X(x, y) = y.

p_{\mathrm{Bool}}(\text{false}, \text{true}) = \text{true} @@ suppose this family picks the second at Bool
f : \mathrm{Bool} \to \mathrm{Int},\ \ f(\text{false}) = 7,\ \ f(\text{true}) = 9 @@ the program that names the pair (7, 9)
p_{\mathrm{Int}}(7, 9) = f(p_{\mathrm{Bool}}(\text{false}, \text{true})) = f(\text{true}) = 9 @@ the square for f
\htmlClass{new}{p_X(x, y) = y \text{ at every type}} \quad \blacksquare @@ the two-picks technique

So the count of such programs is the count of members of Bool, 2, one for each answer at the one test pair (false, true). A program that returned the larger of two numbers fits Int × Int → Int, and fails the label for every type: it looked at the type.

47·comp.6A Schema Is a Category

A database keeps tables: Worker, Team and Task, each a set of rows. A column that names a row of another table is an arrow: team : Worker → Team gives each worker’s team, and owner : Task → Team gives each task’s team. The schema, the tables and columns with their paths run in a row, is a category, and the data at one moment is a map of categories from the schema to sets, sending each table to its set of rows and each column to the function it gives.

The join of Worker and Task over Team keeps the pairs (w, k) with team(w) = owner(k). Join-is-limit technique: the join is the limit of the picture Worker → Team ← Task: the part of Worker × Task where the two teams agree, with its two maps to Worker and Task. Proof: a rival Z with maps u to Worker and v to Task, agreeing in Team, gives z ↦ (u(z), v(z)) in Worker × Task by the pair-map technique, and that pair lies in the sift where the teams agree by 47e’s sift-meets technique, in exactly one way.

\text{workers } w_1, w_2, w_3 \text{ in teams } T_1, T_1, T_2 @@ the column team
\text{tasks } k_1, k_2, k_3 \text{ owned by } T_1, T_2, T_2 @@ the column owner
|\mathrm{Worker} \times \mathrm{Task}| = 3 \cdot 3 = 9 @@ the type-counts technique, pairs
\text{join} = \{(w_1, k_1), (w_2, k_1), (w_3, k_2), (w_3, k_3)\} @@ the pairs whose teams agree
\htmlClass{new}{|\text{join}| = 2 \cdot 1 + 1 \cdot 2 = 4} \quad \blacksquare @@ the join-is-limit technique, one team at a time

So a join is fixed by its arrows and not by how the rows are stored: two databases with matched tables, matched so the columns agree, have matched joins, by 47d’s one-matching technique read for this picture.

The accepted names

The category of types and stopping programs is the usual model of a typed functional language, written Hask or Set for short. Pair types are product types, choice types are sum types, tagged unions or Either, and One is the unit type. Turning a program of two inputs into one that hands back a program is currying. A container with map is a functor, written Functor with fmap in Haskell; the map-over technique is the functor laws, and fusing two passes is map fusion. A program for every type is parametrically polymorphic; the held-in-trust statement is relational parametricity, and the only-identity and two-picks techniques are free theorems. A schema read as a category, with data as a functor into Set, is the categorical, or functorial, view of databases, and a join over a common column is a pullback.

Who said it first

Christopher Strachey told parametric polymorphism from the ad hoc kind in 1967. John Reynolds proved the parametricity statement for his polymorphic calculus in 1983, and Philip Wadler drew free theorems from it in 1989. Currying is named after Haskell Curry, and was used by Moses Schönfinkel in 1924. Edgar Codd set out the relational model of databases in 1970, and David Spivak gave the functorial reading of schemas and data migration in 2012.
