39n · proof

Structures that hold data

A program rarely wants a list for its own sake. It wants to do something to it again and again: take the newest item, or the oldest, or the largest; find whether a name is there; add a name and find it later. How the items are laid out in memory decides how many turns each of those jobs costs, and a good layout can turn a count like the size into a count like its log, or into a count that does not grow at all. This step builds five layouts. A pile, where only the top can be reached. A line, where items leave in the order they came. A heap, a tree folded into a list so that the largest item is always on top and each change costs only the height of the tree. A search tree, ordered left to right, whose cost is its depth, and whose depth, if items arrive in random order, the sort that chooses at random has already counted. And a table of slots chosen by a scrambling rule, where the chance of the statistics floor says how crowded a slot will be.

A pile and a line take and give in a fixed number of turns, and a list that doubles when full costs at most three moves an item. A heap keeps the largest on top at a cost of its height, the log of its size. A search tree costs its depth, and random order gives depth about twice the natural log. A table of m slots holding n keys costs about one plus n over m a look.

39n1Piles, lines, and a list that doubles

A pile lets a program put an item on top and take the top item off. A line lets it put an item at the back and take one from the front. With a counter for the top, or one for each end, each is a fixed number of turns. The catch is room: a list in memory has a fixed number of cells. When it is full, take a new list twice as long and copy everything across.

Doubling-array technique: n items put one at a time into a list that starts with one cell and doubles whenever it is full cost fewer than 3n moves in all.

\text{each item written once}: n \text{ moves} @@ the writes themselves
\text{copies at sizes } 1, 2, 4, \ldots, 2^j \text{ with } 2^j < n @@ a copy happens each time the list fills
1 + 2 + \cdots + 2^j = 2^{j+1} - 1 < 2n @@ a geometric sum (22e), and 2ʲ < n
\htmlClass{new}{\text{fewer than } n + 2n = 3n \text{ moves}} \quad \blacksquare @@ on average fewer than 3 an item

Any one put may be slow: the put that triggers a copy of a million items costs a million moves. The total is what is small. A count spread over a whole run like this is honest only when the run is long, and the technique says exactly how long: the bound holds after every put, not just at the end.

39n2A heap

Lay a tree in a list: cell 1 is the top, and the cells below cell i are 2i and 2i + 1. A heap keeps each cell at least as large as the cells below it, so the largest item is always in cell 1. To add an item, put it in the first empty cell and swap it upward while it is larger than the cell above. To take the largest, move the last item to the top and swap it downward with its larger child while a child is larger.

Heap-height technique: a heap of n items has height ⌊log₂ n⌋, so adding an item costs at most that many swaps, and taking the largest at most twice that many comparisons.

\text{level } j \text{ holds cells } 2^j \text{ to } 2^{j+1} - 1 @@ cell i’s children are 2i and 2i + 1: each level doubles
\text{cell } n \text{ is on level } \lfloor \log_2 n \rfloor @@ 2ʲ ≤ n < 2ʲ⁺¹
\text{a swap moves one level} @@ up when adding, down when taking
\text{taking: two comparisons a level} @@ which child is larger, then whether it beats the item
\htmlClass{new}{n = 10^6:\ \ 19 \text{ levels; at most } 19 \text{ swaps to add, } 38 \text{ comparisons to take}} \quad \blacksquare @@ ⌊log₂ 10⁶⌋ = 19

Put n items in and take them all out, largest first, and they come out sorted, in about 2n log₂ n comparisons and no second list: heap sort. A heap is also how a program keeps the next job to do when jobs keep arriving with different urgencies. 40 uses that to find shortest routes; this step leaves the routes there.

39n3A search tree

A search tree keeps at each place one item, with every smaller item somewhere to its left and every larger one somewhere to its right. To find an item, start at the top and go left or right by comparing; to add one, go down the same way and hang it where the path ends. The cost of a search is the depth reached.

Tree-depth technique: if n different items are added to an empty search tree in random order, the average number of comparisons to add them all is 2(n + 1)Hₙ − 4n, the same as the random-pivot sort’s.

i \text{ and } j \text{ are compared} \iff \text{the first added among } i, \ldots, j \text{ is } i \text{ or } j @@ before it, both go the same way at every place; it parts them
\text{the order of adding is random: chance } \tfrac{2}{j - i + 1} @@ each of the j − i + 1 equally likely to be first (30l1)
\text{the same pairs, the same chances, as in 39l2} @@ the first item added is the top: a pivot
\text{average total} = 2(n + 1)H_n - 4n @@ the pivot-chance technique
\htmlClass{new}{n = 10^6:\ \ \text{about } 24.8 \text{ comparisons an item on average, against } 19 \text{ levels at best}} \quad \blacksquare @@ worked by machine

A random order gives a tree only about a quarter deeper than the best. A sorted order gives the worst, a single path n deep. Trees that rebalance themselves after each add keep the depth below about 1.44 log₂ n for every order; 40 uses them to keep things findable.

39n4A table of slots

A hash table has m slots. A scrambling rule turns each key, a name say, into a slot number, and the key goes on a short list in that slot. To find a key, scramble it and look only in its slot. Model the rule as 30’s chance: each key lands in each slot with chance 1/m, independently of the others.

Load-share technique: with n keys in m slots, a look for a key that is there checks on average at most 1 + (n − 1)/m keys, and the chance that some two keys share a slot is 1 − (1 − 1/m)(1 − 2/m)⋯(1 − (n − 1)/m).

\text{each other key shares the slot with chance } \tfrac1m @@ independence (30f2)
\text{average others in the slot} = \tfrac{n - 1}{m} @@ averages add (30g1)
\text{look} \le 1 + \tfrac{n - 1}{m} @@ the key itself, and at most all the others
\text{no two share} = 1 \cdot \tfrac{m - 1}{m}\cdots\tfrac{m - n + 1}{m} @@ branch-product (30l2): each key misses the slots already used
\htmlClass{new}{n = 23,\ m = 365:\ \ 1 - 0.493 = 0.507} \quad \blacksquare @@ worked by machine: more likely than not

So with as many slots as keys, a look costs about 2 checks whatever the size: a count that does not grow. But two keys meet in some slot far sooner than the slots fill: 23 keys in 365 slots, the people in a room with a shared birthday. A table is fast on average and crowded somewhere almost at once; its rule must scramble well, and 39n.6.4 asks what “well” can mean.

The basement · there if you want it

The accepted names

A pile is a stack (last in, first out) and a line a queue (first in, first out). The doubling list is a dynamic array, and spreading the cost of the copies over the run is amortized analysis. A heap is a binary heap and its use for urgent jobs a priority queue; heap sort is heapsort. A search tree is a binary search tree, and those that rebalance are AVL and red–black trees. A table of slots is a hash table, its rule a hash function, two keys in one slot a collision, and n/m the load factor; the shared-slot chance is the birthday problem. Choosing the rule at random is universal hashing. The crosswalk items here are the data-structure and amortized-analysis items of MIT 6.006 and Stanford CS 161.

Who said it first

J. W. J. Williams gave the heap and heapsort in 1964, and Robert Floyd the way to build a heap in linear time the same year. Search trees were described by several people around 1960; Georgy Adelson-Velsky and Evgenii Landis gave the first self-balancing tree in 1962. Hans Peter Luhn proposed hashing at IBM in 1953. Larry Carter and Mark Wegman introduced universal hashing in 1977.

A proof that is not allowed

“A hash table finds a key in about 2 checks, and a search tree takes about log₂ n, so the table is always better.” Not allowed: the table’s count is an average over its scrambling, and it cannot list keys in order, find the next larger key, or promise a worst case without more work. The tree does all three. A count answers one question about a layout, not which layout to use.
