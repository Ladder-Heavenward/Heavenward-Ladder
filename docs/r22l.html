22l · technique

Splitting the work, counted

Merge sort cut a list in half, sorted each half the same way, and zipped the halves together. Its cost was counted on the seventeenth rung, but only for lists whose length is a power of two, and only for that one recipe. Many good recipes work the same way: cut the job into smaller copies of itself, solve the copies, and pay something to cut and to join. This step counts the cost of every recipe of that kind at once. Picture the work laid out in levels, the whole job at the top and the smallest pieces at the bottom. Either the top level costs the most, or every level costs the same, or the bottom wins. Then it counts merge sort for lists of any length, and shows that no sort that only compares can do much better.

A recipe that splits its work has a cost given by its own smaller costs. Lay the work out in levels and add them: the top wins, every level ties, or the bottom wins. Merge sort is a tie, so it costs about the length times the number of halvings, and no sort that only compares does much better.

What this stands on, and where it goes

22l1Unrolling a split

Stands on 17·comp (the merge-count technique), 4b (induction), 17g4 (the log to any base) and 9·cb4 (recursion as sequences).

A rule that gives a cost at size n from the cost at a smaller size is a recursion, as in 4c and 9·cb4. Here the size halves at each call. 17·comp met one: M(2n) = 2M(n) + 2n − 1. Take the plainest of its kind, T(n) = 2T(n/2) + n: two halves solved the same way, and n steps to cut and join.

Unrolling technique: if T(1) = c and T(n) = 2T(n/2) + n at every power of 2 from 2 on, then T(n) = n log₂ n + cn at every power of 2. Divide by n and the halving becomes a plain count: one more for each doubling.

n = 2^k,\ \ S(k) = T(2^k)/2^k @@ name the cost per item at size 2ᵏ
T(2^k) = 2T(2^{k-1}) + 2^k @@ the rule at n = 2ᵏ, for k ≥ 1
S(k) = S(k-1) + 1 @@ divide both sides by 2ᵏ
S(k) = S(0) + k = c + k @@ add 1, k times: induction on k (4b)
\htmlClass{new}{T(n) = n\log_2 n + cn} \quad \blacksquare @@ multiply back by 2ᵏ = n; k = log₂ n (17g4)

S(k) = S(k − 1) + 1 is the rule x ↦ x + 1 fed its own answers, as in 9·cb4. The same division works on 17·comp's rule: M(2ᵏ)/2ᵏ rises by 1 − 1/2ᵏ at each doubling, and adding those back gives n log₂ n − n + 1. The −1 at each merge changes only the part that grows like n. The n log₂ n is the n steps of joining, paid once at each of the log₂ n levels.

22l2Three ways a split can go

Stands on 22l1, 15i1 (the finite geometric sum), 15i3 (the endless sum), 17g (powers and logs) and 22k1 (~).

A recipe that cuts a job of size n into a smaller copies of size n/b, solves each copy the same way, and spends nᵈ steps to cut and to join, has the accepted name a divide and conquer recipe. Its cost obeys T(n) = aT(n/b) + nᵈ. Lay the work out in levels: the whole job is level 0, its a pieces are level 1, their pieces level 2, down to pieces of size 1.

Master technique: let a ≥ 1, b ≥ 2 and d ≥ 0, let T(1) = c ≥ 0 and T(n) = aT(n/b) + nᵈ at powers of b, and let r = a/bᵈ; then along the powers of b, T(n) ~ nᵈ/(1 − r) if r < 1, T(n) ~ nᵈ log_b n if r = 1, and T(n) ~ (c + 1/(r − 1)) n^(log_b a) if r > 1. r is how much each level costs beside the one above it.

\text{level } j:\ a^j \text{ pieces, each of size } n/b^j @@ each cut makes a pieces, b times smaller
\text{work at level } j = a^j\big(\tfrac{n}{b^j}\big)^d = n^d r^j @@ the joining cost of each piece, added; r = a/bᵈ
T(n) = c\,a^k + n^d(1 + r + \cdots + r^{k-1}),\ \ n = b^k @@ levels 0 to k − 1, then aᵏ pieces of size 1 at cost c each
a^k = n^{\log_b a} @@ both are exp(ln a · ln n / ln b) (17g)
r < 1:\ \ T(n) \sim \tfrac{n^d}{1 - r} @@ the sum heads to 1/(1 − r) (15i3), and c aᵏ/nᵈ = c rᵏ heads to 0
r = 1:\ \ T(n) = n^d(\log_b n + c) \sim n^d\log_b n @@ every level costs nᵈ, and there are k = log_b n levels
r > 1:\ \ T(n) = \big(c + \tfrac{1}{r - 1}\big)a^k - \tfrac{n^d}{r - 1} @@ the finite sum is (rᵏ − 1)/(r − 1) (15i1), and nᵈrᵏ = aᵏ
\htmlClass{new}{r > 1:\ \ T(n) \sim \big(c + \tfrac{1}{r - 1}\big)n^{\log_b a}} \quad \blacksquare @@ nᵈ/aᵏ = r⁻ᵏ heads to 0
  • Merge sort: a = 2, b = 2, d = 1, so r = 1. Every level costs n, and there are log₂ n levels: n log₂ n, as 22l1 found.
  • Looking up a name in a sorted list: check the middle, keep one half. T(n) = T(n/2) + 1, so a = 1, b = 2, d = 0, r = 1. The cost is log₂ n: about 20 looks in a list of a million names.
  • Multiplying two n-digit numbers the school way takes n² products of single digits. Cut each number into halves: (x·10ᵐ + y)(u·10ᵐ + v) = xu·10²ᵐ + ((x + y)(u + v) − xu − yv)·10ᵐ + yv. That is three products of half size, not four, plus some adding. So a = 3, b = 2, d = 1, r = 3/2, and the bottom wins: about n^(log₂ 3), close to n^1.585. At 1024 digits, 3¹⁰ = 59 049 digit products against 1 048 576.

Which case holds is a contest between two numbers: a, how many pieces each cut makes, and bᵈ, how much cheaper the joining gets at each level down. The work at the top is nᵈ. The number of pieces at the bottom is n^(log_b a). Whichever is larger in rank (22k2) sets the cost, and when they tie, the levels add.

22l3Every n, not only powers of two

Stands on 17·comp (merging s items with t takes at most s + t − 1 comparisons), 4g12 (strong induction) and 22l1.

17·comp proved its count for powers of 2 only. A list of 7 splits into 3 and 4, and the halves are uneven. Let W(n) be the most comparisons merge sort makes on any list of n items. For n ≥ 2, the halves have n₁ and n₂ items, with n₁ ≤ n₂ ≤ n₁ + 1 and n₁ + n₂ = n. Sorting the halves costs at most W(n₁) + W(n₂), and the merge at most n − 1. So W(1) = 0 and W(n) ≤ W(n₁) + W(n₂) + n − 1. Let L(n) be the number of halvings that bring n down to 1: the least k with n ≤ 2ᵏ.

Halvings technique: for every n ≥ 1, merge sort makes at most n·L(n) comparisons, and n·L(n) < n log₂ n + n. The proof leans on every smaller size at once, so it is a strong induction.

W(1) = 0 = 1 \cdot L(1) @@ one item needs no comparison, and no halving
n \ge 2,\ k = L(n):\ \ n_1 \le n_2 \le 2^{k-1} @@ n₂ is n/2 or (n + 1)/2, and an odd n ≤ 2ᵏ is at most 2ᵏ − 1
L(n_1) \le k - 1,\ \ L(n_2) \le k - 1 @@ each half fits in 2ᵏ⁻¹
W(n) \le n_1(k - 1) + n_2(k - 1) + n - 1 = nk - 1 @@ strong induction (4g12): the claim at every smaller size; n₁ + n₂ = n
2^{k-1} < n \Rightarrow k < \log_2 n + 1 @@ k is the least with n ≤ 2ᵏ, so 2ᵏ⁻¹ is too small
\htmlClass{new}{W(n) \le n\,L(n) < n\log_2 n + n} \quad \blacksquare @@ the last two lines

So merge sort is O(n log n) for every n, not only at powers of 2. At n = 1000, ten halvings bring 1000 down to 1, and the bound is 10 000. Running the rule with equals in place of at most gives 8977. Both are about n log₂ n, which at n = 1000 is about 9966.

22l4No sort does much better

Stands on 4j (n! orders), 22k3 (the factorial-fence technique), 22l3 and 10d (the squeeze).

Merge sort is fast. Could some cleverer sort be faster by more than a fixed factor? Count what a sort can learn. A sort that learns about the items only by comparing two of them gets a yes or a no each time. The answers so far decide what it does next.

Answer-count technique: a sort that learns only by comparing makes at least log₂ n! comparisons on some list of n different items, and log₂ n! ~ n log₂ n.

\text{at most } m \text{ comparisons on every list} @@ suppose it, for some m
\text{the runs fork at most } m \text{ times deep: at most } 2^m \text{ ends} @@ each answer is yes or no
\text{two lists that get the same answers get the same moves} @@ the sort learns nothing else about the items
\text{the } n! \text{ orders of } n \text{ different items need } n! \text{ different moves} @@ one rearrangement sorts only one order (4j)
2^m \ge n! \Rightarrow m \ge \log_2 n! @@ log₂ rises (17g4)
n\log_2\tfrac{n}{e} + \log_2 e \le \log_2 n! \le n\log_2 n @@ the factorial fence (22k3); n! ≤ nⁿ
\htmlClass{new}{\log_2 n! \le W(n) < n\log_2 n + n,\ \text{so } W(n) \sim n\log_2 n} \quad \blacksquare @@ merge sort is such a sort; 22l3; divide by n log₂ n and squeeze (10d)

This is the full answer to why 17·comp's merge sort costs about n log₂ n. It never costs more than n log₂ n + n. And no sort that only compares can promise less than log₂ n!, which grows alike. With a million items, every such sort makes about 18.5 million comparisons on some list, merge sort makes at most about 19.0 million, and selection sort makes 500 billion.

The answer count is a different kind of proof from the others on this step. It does not count one recipe. It counts every recipe at once, including the ones nobody has thought of yet, by counting what they could possibly learn.

The basement · there if you want it

The accepted names

A rule like T(n) = 2T(n/2) + n is a recurrence relation, or recurrence. Unrolling it is the iteration method; laying the work out in levels draws a recursion tree. The master technique is the master theorem. The answer count is the information-theoretic (or decision-tree) lower bound for comparison sorting. Looking up a name by halves is binary search. The three-product split is Karatsuba multiplication.

Who said it first

John von Neumann wrote out merge sort in 1945, and John Mauchly described binary search in 1946. In 1960 Andrey Kolmogorov conjectured that multiplication needs about n² digit products; Anatoly Karatsuba, a student in his seminar, found the three-product split within a week, published in 1962 (22l.4.5). Jon Bentley, Dorothea Haken and James Saxe gave a general method for such recurrences in 1980, and the name master theorem spread from the textbook of Thomas Cormen, Charles Leiserson and Ronald Rivest (1990). The log₂ n! bound for sorting was known by the 1950s; Lester Ford and Selmer Johnson (1959) built a sort that comes close to it for small n.
