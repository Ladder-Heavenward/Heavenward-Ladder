Can a Program Run Forever?

Can a program run forever? A program is a list of steps for a machine, and many programs say: do this step again, and again, until something is so. That is a loop. A loop that should stop and does not is one of the oldest troubles in computing. The screen freezes, the fan spins, and nobody can tell whether the machine is nearly done or will never be done. Yet some loops are meant to run forever, like the one that turns a traffic light from green to yellow to red and back. What makes the question hard is that watching cannot settle it. You can watch a loop stop. You can never watch it run forever, since every watch ends. This page treats a loop as the next-one rule of this rung, run by a machine, with a test that can stop it. It proves that one loop never stops, from the fact that the next one after a set is never empty. It shows a loop that runs forever by coming back to where it was, and a loop that stops because its work shrinks. And it shows why no program can read every program and always tell whether it stops.

A loop does one step again and again, and checks its test before each pass. It stops the first time the test is false. A loop whose step always makes a next one, with the test “not yet empty”, never stops, since the next one after a set is never empty. A loop that comes back to where it was does the same passes again, and never stops. A loop that takes a member out of a list you can write down, and puts nothing back, empties the list and stops. Shrinking is not enough for an endless set. And no checker can tell, for every program, whether it stops.

3comp1A Loop Is the Next-One Rule, Run by a Machine

3c1 called feeding a move its own output, again and again, iterating it. A machine iterates with a loop. A loop has a step, called its body, and a test. Before each pass the machine checks the test, as 2·comp’s machine checks a condition. If the test is true, it does the body once and checks again. If the test is false, it stops.

Here is a loop in plain words, built from 3c’s next one:

start: x is 0 while x ≠ 4: x becomes S(x)

The machine checks 0 ≠ 4: true, so x becomes 1. Then 1 ≠ 4, and x becomes 2. Then 2, then 3, then 4. Now the test 4 ≠ 4 is false, and the loop stops at 4. Each value it passed through is a name of 3c5, made by S from the one before.

A loop does its body again and again, checking its test before each pass, and stops the first time the test is false. A loop that stops is one whose test, sooner or later, comes out false.

3comp2A Loop That Never Stops

Change the test:

start: x is 1 while x ≠ ∅: x becomes S(x)

Before the first pass, x is 1, which has 0 as a member. So 1 ≠ ∅, and the test is true. Before any later pass, x has just been made by the body. Let y be the value the body was given. Then x is S(y), and the next-never-empty technique says S(y) ≠ ∅. Nothing was supposed about y, so this is true before every later pass.

So the test is true before every pass, and the loop never stops. That is a proof about every pass the loop will ever make. No one watched them. A loop whose body always makes a next one, with the test “not yet empty”, never stops.

It never comes back to a value it had, either. 3c10 found that the names 0 to 4 and S(4) differ, each from each, and 3c’s run never lands where it has been. That every value is new, however far the loop runs, is held in trust here; rung 4 proves that different sets have different next ones.

A test can also miss. Start the first loop from {1} instead of 0. Each pass makes a next one of a set outside the run, and 3c13 found that it stays outside. So x is never 4, the test never fails, and the loop that stopped from 0 runs forever from {1}.

3comp3Forever by Coming Back

Not every loop that runs forever is a mistake. At a crossing in Eugene, the signal is run by a loop like this one:

start: x is green while x is a colour of the signal: x becomes the colour after x (after green comes yellow, after yellow red, after red green)

The run is green, yellow, red, green, and there it is back where it started. The test looks only at x, and the body looks only at x. So from green, the loop does exactly what it did the last time it was at green. It makes yellow, then red, then green, again and again.

Back-again technique: a loop whose test and body look only at x, and that comes back to a value it had, runs forever. Here is why. When the loop was at that value before, it went on, so the test was true there. Now it is at the same value, so the test is true again, and the body makes the same next value. From there it repeats what it did, and comes back again.

So there are two ways to run forever. The signal comes back, round and round. The next-one loop of 3·comp2 goes on and never comes back. A loop that comes back is easy to catch: keep a list of the values it has had, and stop when one turns up again. A loop that never comes back makes a new value on every pass, and the list never helps.

3comp4A Loop Whose Work Shrinks

When the ferry docks at Bainbridge Island, the cars on its deck drive off, one at a time. A program that tracks the deck looks like this:

start: u is the set of cars on the deck while u ≠ ∅: pick a member c of u; u becomes u ∖ {c}

Each pass takes a member out and puts nothing back. The new u is a sift of the old one, so it is part of the old one (2e8). Take u = {van, truck, bike}. The passes might give {truck, bike}, then {bike}, then ∅, and the loop stops. Every order of picking empties it.

Shrinking-work technique, held in trust: a loop that takes a member out of a set you can write down, on each pass, and puts nothing back, empties the set and stops. For any one set you write down, you can write out the passes and watch it empty. That it works for every such set at once is a claim about how many members a set has, and rung 4 builds that.

3c11’s merging back is a shrinking loop too. Start x at 4, and while x ≠ 0, let x become ⋃x. The run is 4, 3, 2, 1, 0, and it stops.

Now take away the words “you can write down”. Let I be an inductive set, which the axiom of 3d gives. Run the deck loop on I, taking out 0, then 1, then 2, and on. Each pass takes a member out, and I still never empties. The next one after the member taken out last is in I, by the step part of inductive. It was never taken out, since every member taken out so far came before it; that last fact is held in trust until rung 4. Shrinking is enough for a set you can finish writing. It is not enough for an endless one.

3comp5Why Nobody Can Always Tell

The page has settled three loops by argument: one never stops, one comes back, one shrinks and stops. Could a program do this work for us? Picture a checker, a program that reads any program and answers “stops” or “runs forever”, and is always right.

Here is a sketch of why there can be none, held in trust. Build a program that reads its own text, asks the checker about itself, and does the opposite. If the checker says “stops”, it runs a loop that never stops. If the checker says “runs forever”, it stops at once. Suppose the checker says “stops”: then the program runs forever, and the checker was wrong. Suppose it says “runs forever”: then the program stops, and the checker was wrong again. Both cases clash with “always right”, so refute: no such checker.

That is the shape of 2e4’s catalogue and 2e14’s outsider set: a thing asked about itself, made to do the opposite. The full argument needs programs as objects that programs can read, and it is much higher up the ladder. No checker can read every program and always tell, rightly, whether it stops. Each loop on this page was settled by an argument made for that loop, and no single method makes them all.

Anexact, yet rigorous · the universe, gathering

Watch a loop run, and every watch ends. You see that it has not stopped yet, and never that it will not. 3d found the same of the universe: the rule for the next cell can be written down, and the finished collection never turns up.

Watching can show that a loop stops, and only an argument can show that it does not.

So a claim that a loop runs forever is never seen. It is argued, as 3·comp2 argued it, by speaking of every pass at once.

A machine at a lab has run a loop for a year without stopping. What would it take to know it never will?

Accepted names

A loop with a test checked before each pass is a while loop; its step is the loop body. A loop that never stops is an infinite loop. A loop that comes back to a value it had is in a cycle. Something that shrinks on every pass and shows a loop must stop is a loop variant, and showing that a program stops is proving termination. The question whether a program stops is the halting problem, and a question no step-by-step method settles is undecidable.

Who said it first

David Hilbert and Wilhelm Ackermann asked in 1928 for a method that settles, step by step, whether any statement of logic follows from others: the decision problem. In 1930 Hilbert closed a radio address with “We must know; we will know.” In 1936 Alonzo Church and Alan Turing each showed there is no such method. Turing’s argument is the opposite program of 3·comp5, made precise. Those are the two sides of 3·comp.7.5. Turing (1949) and Robert Floyd (1967) showed how to prove that a loop stops by finding something that shrinks on every pass and cannot shrink forever.
