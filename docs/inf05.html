How Does Data Move When the Schema Changes?

How does data move when the schema changes? Rung 47 read a database as a map from its schema, the tables and columns, to sets. A company that changes its schema, splitting a table or merging two, must move its data from the old layout to the new. A map of schemas gives three ways to move data along it: backward, by reading through the map; forward, by gluing rows together; and forward, by joining them. The two forward moves are left and right of the backward one, as rung 47 named such pairs, and that fixes them. The same view shows that a query built from ands and somes is a small database of its own, and answering it is finding maps, a fact known since 1977. Migration built on the three moves was set out from 2010 and published in 2012. When a schema adds rules saying that two paths agree, the forward moves can ask questions no machine decides.

Data on a schema S is a map of categories I : S → Set. A map of schemas F : S → T gives ΔF(J) = J ∘ F, pulling data on T back to S, and two forward moves ΣF ⊣ ΔF ⊣ ΠF. Sending two tables to one: Σ glues, I(A) ⊔ I(B); Π joins, I(A) × I(B). A query with only ands and somes is a small database Q, and its answers in I are the maps from Q into I.

inf5.1Data as a Map From the Schema

47·comp.6 made a schema a category: tables as things, columns that point to another table as arrows, and paths run in a row. The data at one moment is a map of categories I from the schema to sets: each table goes to its set of rows, each column to a function between the sets of rows.

A map of schemas F : S → T sends each table of S to a table of T and each column to a path, keeping running in a row. Given data J on the new schema T, read it on the old one by going through F.

Pull-data technique: for F : S → T and data J on T, ΔF(J) = J ∘ F is data on S, and a map of data on T pulls back to a map of data on S.

J : T \to \mathbf{Set},\ F : S \to T @@ data on T, a map of schemas
J \circ F : S \to \mathbf{Set} @@ maps of categories in a row are one (47b1)
\alpha : J \Rightarrow J^{\prime} \text{ gives } \alpha_{F(s)} \text{ at each table } s @@ read the natural map at the tables F names
\htmlClass{new}{\Delta_F(J) = J \circ F \text{ is data on } S} \quad \blacksquare @@ each square for an arrow of S is a square for its image in T

inf5.2Two Tables Into One

Start with the smallest case. S has two tables A and B and no columns between them; T has one table C; F sends both A and B to C. Pulling back copies: Δ(J) puts J(C) at A and at B. There are two ways to move data I on S forward to C.

Glue-and-join technique: for F sending A and B to C, Σ(I)(C) = I(A) ⊔ I(B), the rows of both tables side by side, is left of Δ; Π(I)(C) = I(A) × I(B), the pairs of rows, is right of Δ.

\text{maps } I \Rightarrow \Delta(X) = \text{pairs } (I(A) \to X,\ I(B) \to X) @@ a natural map from I to the copied X is one function per table
\text{pairs } (I(A) \to X,\ I(B) \to X) \cong \text{functions } I(A) \sqcup I(B) \to X @@ a sum is fixed by its maps out (47e)
\text{maps } \Delta(X) \Rightarrow I \cong \text{functions } X \to I(A) \times I(B) @@ a product is fixed by its maps in (47d)
\htmlClass{new}{\Sigma \dashv \Delta \dashv \Pi,\ \Sigma(I)(C) = I(A) \sqcup I(B),\ \Pi(I)(C) = I(A) \times I(B)} \quad \blacksquare @@ 47f1’s left and right

inf5.3Adding a Table

Now let S have one table Worker, and T have Worker with a column team : Worker → Team. F puts S inside T. Data on S is a list of workers; data on T must also say what the teams are and which team each worker is on. Pulling back forgets the teams.

New-table technique: moving a table of workers forward into the schema with teams, Σ gives each worker a team of their own, and Π puts every worker on one team.

\text{maps } \Sigma(I) \Rightarrow J \leftrightarrow \text{functions } I(\mathrm{Worker}) \to J(\mathrm{Worker}) @@ Σ ⊣ Δ: a map out of Σ(I) is fixed on the workers
\Sigma(I)(\mathrm{Team}) = I(\mathrm{Worker}),\ \text{team} = \text{do-nothing} @@ the freest choice: no two workers share a team unless forced
\text{maps } J \Rightarrow \Pi(I) \leftrightarrow \text{functions } J(\mathrm{Worker}) \to I(\mathrm{Worker}) @@ Δ ⊣ Π: no arrow of T leaves Team, so Team asks nothing
\htmlClass{new}{\Pi(I)(\mathrm{Team}) = \{\ast\}\text{, one team}} \quad \blacksquare @@ a set of one is the product of nothing

For three workers w₁, w₂, w₃, Σ makes three teams of one; Π makes one team of three. A migration tool must say which it means, and these are the only two that the arrows allow.

inf5.4A Query Is a Small Database

A query with only ands and somes asks for rows linked in a pattern: “pairs of workers on one team” asks for w₁, w₂ and some t with team(w₁) = t and team(w₂) = t. Draw the pattern as data Q on the same schema: two Worker rows, one Team row, both pointing to it.

Query-is-map technique: the answers to a query with only ands and somes in data I match the maps of data from its pattern Q into I.

\alpha : Q \Rightarrow I \text{ picks } \alpha(w_1), \alpha(w_2) \in I(\mathrm{Worker}),\ \alpha(t) \in I(\mathrm{Team}) @@ a map sends each pattern row to a data row
\text{team}(\alpha(w_i)) = \alpha(\text{team}(w_i)) = \alpha(t) @@ naturality: columns are kept
\text{each answer } (w_1, w_2, t) \text{ gives one such } \alpha @@ and back
\htmlClass{new}{\text{answers} \leftrightarrow \text{maps } Q \Rightarrow I} \quad \blacksquare @@ the ands are the squares, the somes are the pattern’s extra rows

So 47·comp.6’s join, Worker ← Team → Task read as pairs agreeing in Team, is a query, and its pattern is that picture. Two queries ask the same exactly when their patterns map into each other, which reduces checking two queries to finding maps between two small databases.

Open questions

These are open: the field is still asking them. There is no key; a good attempt is a reason, a guess, or a better question.

∞Φ.oq.1A schema can carry rules saying that two paths agree, such as “a worker’s team’s manager is the worker’s manager”. With such rules, moving data forward can require deciding whether two paths are equal, and with enough rules that question is the kind 41e showed no machine decides. Which fragments of schemas with rules keep the forward moves decidable and fast is open.
A short history · told from more than one side

How we got here

Relational databases were proposed in 1970, with tables and a short list of operations. In 1977 a paper showed that queries with only ands and somes are small databases of their own, so that answering one is finding maps and checking whether two ask the same is finding maps between their patterns.

The left and right moves along a map of categories were named for the topologist who introduced left-and-right pairs in 1958.

From 2010 the three moves were proposed as the operations of data migration, with a schema read as a category, and software for moving and merging databases was built on them in the years after. Rules that say paths agree made some moves hard to compute.

The accepted names

Data on a schema is a copresheaf or instance; ΔF is pullback or restriction, ΣF the left Kan extension and ΠF the right Kan extension along F. A query with only ands and somes is a conjunctive query, its pattern the canonical database, and answers as maps is the homomorphism theorem; checking two queries is query containment. Rules that paths agree are path equations, and deciding them is a word problem.

Who said it first

Edgar Codd, the relational model (1970). Ashok Chandra and Philip Merlin, conjunctive queries and homomorphisms (1977). Daniel Kan, adjoint functors (1958). David Spivak, “Functorial data migration” (2010 preprint; Information and Computation, 2012); Spivak and Ryan Wisnesky, relational foundations and the software that followed (2012-15).
