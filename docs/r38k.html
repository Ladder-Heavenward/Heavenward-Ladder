38k · proof

How long a program takes

The machine of the last step multiplied three by four in thirty-nine turns, and the count grew by nine for each one added to the second number. That kind of count is the subject here. A program’s time is the number of turns its machine takes, and the count can be read off the program before it is run: a loop run so many times, with so many instructions inside, costs their product. The exact count depends on the machine, and a different machine changes it by a fixed factor at most, so what is worth saying about a program is the family its count belongs to: steady, growing like the log, like the size, like the size times its log, like the square, or like two raised to the size. The rung on endless sums ranked those families already. This step reads them as what a machine can do. A thousand times faster machine solves a problem a thousand times bigger in the same time if the count grows like the size, about thirty times bigger if it grows like the square, and only ten more items bigger if it grows like two to the size. Then the step counts the other thing a program spends, the memory it needs, and what digital storage costs and buys.

Read a program’s turns off the page: a loop costs its instructions times its rounds. A different machine changes the count by a fixed factor, so the family is what matters. A faster machine buys a much bigger problem for slow-growing counts and almost nothing for two to the size. Memory is counted in bits, and a stored bit is copied exactly.

38k1Counting turns

The time a program takes on an input is the number of turns of 38j2’s loop before it stops. A run of instructions with no jump back costs one turn each. A loop whose body has b instructions and goes round r times costs br, plus its test. Loops inside loops multiply, and sums of rounds add by 4k.

Loop-count technique: a loop whose body takes b turns and runs r times, with s turns outside it, takes br + s turns; a loop inside a loop whose inner rounds are r₁, r₂, …, takes b(r₁ + r₂ + ⋯) plus the outer loop’s own turns.

\text{38j3: body } 9 \text{ turns},\ k \text{ rounds},\ 3 \text{ outside} @@ read off the program
9k + 3 @@ the technique
\text{look at each of } n \text{ cells for a match: body } 5,\ n \text{ rounds},\ 2 \text{ outside} @@ a search through a list, in this machine’s instructions
\text{compare every pair: inner rounds } n - 1, n - 2, \ldots, 0 @@ for each cell, every cell after it
\htmlClass{new}{5n + 2\ \text{ and }\ b\,\tfrac{n(n - 1)}{2} + \ldots} \quad \blacksquare @@ the sum of the first n − 1 numbers (4k)

“Takes” means at most, over the inputs of a given size: the worst case. A search that finds its match in the first cell is quick; the count that matters is the one that holds for every input of size n. The average over inputs is a second count, and 38l uses 30’s chance to find it.

38k2The family is what survives

Change the machine and the counts change. A machine with only adding by one would need many turns where 38j’s needs one add; a machine with a multiply instruction would need one where 38j’s needs a loop. If each instruction of one machine can be done by at most c instructions of another, the second’s count is at most c times the first’s.

Machine-change technique: if each turn of one machine is done in at most c turns of another, a count that is O(f(n)) on the first is O(f(n)) on the second. That every reasonable machine can mimic every other in this way is held in trust until 39 makes the machines exact.

T_1(n) \le C f(n) \text{ for } n \ge N @@ O as 22k1 defines it
T_2(n) \le c\,T_1(n) @@ each turn done in at most c turns
T_2(n) \le cC f(n) \text{ for } n \ge N @@ chain the two
\htmlClass{new}{T_2(n) = O(f(n))} \quad \blacksquare @@ the constant cC, the same N
  
n = 10^6:\ \ \tfrac12 n^2 = 5\cdot10^{11} \text{ turns} @@ comparing every pair
5\cdot 10^{11} / 10^9 = 500 \text{ s} @@ over eight minutes
n\log_2 n \approx 2\cdot10^7 \text{ turns} @@ log₂ 10⁶ ≈ 19.9 (17d)
\htmlClass{new}{2\cdot10^7 / 10^9 = 0.02 \text{ s}} \quad \blacksquare @@ the ranks of 22k2, in seconds

So what is worth saying about a program is its family, read with 22k’s big O: constant, log n, n, n log n, n², n³, 2ⁿ, ranked by 22k2. The constants matter in practice, and a program in a lower family with a huge constant can lose for every n anyone meets. But no constant survives a change of family for long.

38k3What a faster machine buys

Fix a time, a second say, and ask how big a problem fits in it. Then make the machine s times faster.

Faster-machine technique: on a machine s times faster, in the same time, a count of n fits s times as large a problem, a count of n² fits √s times as large, and a count of 2ⁿ fits a problem only log₂ s items larger.

n_1 = M,\ \ n_2 = sM @@ count n: s times as many turns, s times the size
n_1^2 = M,\ \ n_2^2 = sM \Rightarrow n_2 = \sqrt{s}\,n_1 @@ count n²
2^{n_1} = M,\ \ 2^{n_2} = sM \Rightarrow n_2 = n_1 + \log_2 s @@ count 2ⁿ; take logs (17d)
\htmlClass{new}{s = 1000:\ \ 1000 \text{ times},\ \ 31.6 \text{ times},\ \ \text{about } 10 \text{ more items}} \quad \blacksquare @@ √1000 ≈ 31.6, log₂ 1000 ≈ 9.97

Machines have grown about a thousand times faster every twenty years or so for decades, and 38·eng asks why that slowed. For a program whose count grows like 2ⁿ, those decades bought ten more items each. A problem is practical or not by its family, much more than by its machine, and 39 asks which problems have no program in a low family at all.

38k4Memory counts too

A program also spends memory: cells, and in the end bits. A number below 2ᵇ needs b catches (38h4), so a list of n such numbers needs nb bits, and reading all of it takes at least about n turns.

Storage-count technique: n items each one of 2ᵇ patterns take nb bits, and fewer bits cannot hold every list of n items. A row of fewer than nb catches has fewer than 2^(nb) patterns, so two lists would share one.

\text{a photo}: 12\cdot10^6 \text{ dots},\ 3 \text{ colours of } 8 \text{ bits} @@ 2²⁴ patterns a dot (36’s three numbers, each a byte)
12\cdot10^6 \cdot 24 = 2.88\cdot10^8 \text{ bits} = 36\,000\,000 \text{ bytes} @@ a byte is 8 bits
\text{a song}: 44\,100 \text{ samples a second},\ 16 \text{ bits},\ 2 \text{ ears},\ 180 \text{ s} @@ 32k’s rate
\htmlClass{new}{44\,100 \cdot 16 \cdot 2 \cdot 180 / 8 \approx 31.8 \text{ million bytes}} \quad \blacksquare @@ the technique

What digital storage buys is exactness. Each bit is read against a threshold (38b4), so a copy of a copy of a copy has the same bits, misread only at the known rate, which codes push lower still. A tape of sound loses a little at every copy and never gets it back. What it costs is the count: every bit must be stored, and moved, and 38c3 limits how many a wire moves a second. That is why the file sizes above are usually cut, by 32·comp’s and 30·comp’s ways of dropping what the eye and ear will not miss, or what is predictable.

The basement · there if you want it

The accepted names

A program’s count of turns is its running time or time complexity, and the worst case over inputs of size n is the worst-case time; the families are constant, logarithmic, linear, linearithmic (n log n), quadratic, cubic, and exponential time. The machine-change technique is the invariance behind the cost model, and the claim held in trust, that every reasonable machine mimics every other within a fixed factor or a power, is the extended (or strong) Church–Turing thesis. A program’s memory is its space complexity. The practical-means-polynomial camp of 38k.6.4 is Cobham’s thesis (also credited to Edmonds). The crosswalk items here are AP Computer Science A 2.12 (informal run-time analysis), AP Computer Science Principles 3.17 (algorithmic efficiency) and NGSS HS-PS4-2 (digital information storage).

Who said it first

Juris Hartmanis and Richard Stearns founded the counting of running times as functions of the input size in 1965. Alan Cobham (1965) and Jack Edmonds (1965) proposed polynomial time as the mark of a practical problem. Donald Knuth made big O the language of program counts in The Art of Computer Programming, from 1968, and argued in 1976 for its letters Ω and Θ.

A proof that is not allowed

“Program A took 2 seconds on my laptop and program B took 3, so A is in a lower family.” Not allowed: one run on one input of one size, on one machine, measures one count. The family is a claim about every size, and two programs can trade places as n grows. Counts are read off the program, or measured at many sizes and fitted, and the fit is a guess under the small case with its range said.
