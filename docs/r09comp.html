How Does a Shop Find One Order Among Millions?

How does a shop find one order among millions? A bakery that takes orders online keeps every order, every customer and every cake in tables, and answers questions like “which orders go to Fernwood on Friday?” in a blink. The tables look like spreadsheets, but under them is the mathematics of rungs 2 and 9: a row is a function, a table is a set of rows, a key is a one-to-one function, and a question is a sift. This page builds those four ideas, joins two tables through a key, and shows why each fact should be stored in one place only.

A row gives each column name a value, so it is a function from the column names. A table is a set of rows, so equal rows are one row. A key is a column whose map from rows to values is one-to-one, so it runs backwards to a single row. Ask by sifting rows and restricting each row to the columns you want. Join two tables by sifting their product for matching keys, and store each fact once, reaching it by composing.

9comp1A Row Is a Function, a Table Is a Set

Here is part of the bakery’s table of customers.

idnamestreet
17ClaireFernwood
23RandyHill Road
31JoyFernwood

From here on, on this page, a row is a function from the table’s column names to values, as in 9: the first row sends id to 17, name to Claire and street to Fernwood. A table is a set of rows.

Because a table is a set, the same-members axiom (2e) says that writing a row twice adds nothing: two rows that give every column the same value are one row. And a set has no order, so the order the rows are printed in says nothing.

9comp2A Key Picks Out One Row

Two customers can share a name, and two share a street. The id column is different in every row. From here on, on this page, the column map of a column c sends each row r to r(c). A key is a column whose column map is one-to-one (9c): different rows always have different values there.

\text{id} : \text{rows} \to \text{values},\ r \mapsto r(\text{id}) @@ the column map
r(\text{id}) = s(\text{id}) \Rightarrow r = s @@ id is a key: the map is one-to-one
\text{restrict to the values it takes} @@ 9d’s restriction makes it onto them
\htmlClass{new}{\text{id}^{-1}(23) = \text{Randy’s row}} @@ 9d: a one-to-one onto map runs backwards

Street is not a key: Claire’s row and Joy’s row both give Fernwood, so the street map sends two rows to one value and cannot run backwards. A key is a column you can run backwards: one value, one row.

9comp3Asking a Table a Question

A question picks some rows and some columns. “Who lives on Fernwood?” keeps the rows whose street is Fernwood, then keeps only their names. The first part is a sift (2f): the set of rows of the table for which the condition holds.

\{r \in \text{customers} : r(\text{street}) = \text{Fernwood}\} @@ the sift axiom (2f)
= \{r_1, r_3\} @@ Claire’s row and Joy’s
r \mapsto r \text{ restricted to } \{\text{name}\} @@ keep one column: 9d’s restriction, row by row
\htmlClass{new}{\{\text{Claire}, \text{Joy}\}} @@ the answer

Restricting can make two rows equal. Ask “which streets have customers?” and Claire’s row and Joy’s both restrict to Fernwood. As a set, the answer lists Fernwood once. An answer is a set too, so cutting columns can merge rows.

9comp4Joining Two Tables

Orders are kept in a second table. Each order names its customer by id, not by name.

ordercakedaycustomer
501lemonFriday17
502carrotFriday23
503lemonSaturday31

To ask “which orders go to Fernwood on Friday?”, pair every order with every customer, a product as in 2i, and sift for the pairs where the order’s customer is the customer’s id. That sift is the join. Then sift again for Fernwood and Friday.

\text{orders} \times \text{customers}:\ 3 \cdot 3 = 9 \text{ pairs} @@ the products-exist technique (2i); stages-multiply (4k)
\{(o, r) : o(\text{customer}) = r(\text{id})\} @@ the join: one customer for each order, since id is a key
= \{(501, 17), (502, 23), (503, 31)\} @@ 3 of the 9 pairs
\ldots : r(\text{street}) = \text{Fernwood},\ o(\text{day}) = \text{Friday} @@ sift again
\htmlClass{new}{\text{order } 501} @@ Claire’s lemon cake

The customer column of the orders is a function from orders to ids, and id runs backwards to rows. Composed (9b), they send each order to its customer’s row, and then to the street: following a key from one table into another is composing functions.

9comp5Store Each Fact Once

Why not write the street in every order row and skip the join? Because then the street is stored many times, and the copies can disagree. If Joy moves and one of her orders is changed while another is not, the table now says she lives in two places. No join can tell which is right.

Stored once, in the customer table, the street is reached from any order by the composition of 9comp4. Change it in one place and every order follows. A fact stored once cannot disagree with itself. Designers of databases split tables until every fact that depends on a key is stored only in the table where that key is the key.

9comp7An Index Halves the Search

A key picks out one row (9comp2), but finding that row by reading every row takes up to a million looks in a million rows. An index keeps the keys in order beside where each row lives. Look at the middle key: the one wanted is above or below, and half the rows are gone.

\text{each look halves what is left} @@ 
2^{20} = 1\,048\,576 \ge 1\,000\,000 @@ 
\text{so at most } 20 \text{ looks} @@ not a million
\htmlClass{new}{\text{a billion rows: } 2^{30} > 10^9,\ \text{only } 30 \text{ looks}} @@ ten more looks for a thousand times the rows

Halving-index technique: keep the keys in order and look at the middle one each time; the count of looks is how many doublings it takes to pass the number of rows. Real tables keep a hundred or so keys at each step, so three steps reach a million rows. Shown in a run: a store’s order table of a million rows, searched by order number through its index, finds the one order in 20 looks, where reading row by row took half a million on average.

Accepted names

A table is a relation, a row is a tuple and a column name is an attribute. A key is a primary key or a candidate key; a column that holds another table’s key is a foreign key. Sifting rows is selection, restricting to columns is projection, and the sifted product is a join. Storing each fact once is normalisation, and the trouble with copies is an update anomaly. Most databases are asked their questions in a language called SQL.

Who said it first

Edgar F. Codd set out tables as sets of rows, and questions as operations on them, in “A Relational Model of Data for Large Shared Data Banks”, 1970.
