How Does One Chip Run a Hundred Programs?

How does one chip run a hundred programs? A phone plays music, fetches mail and draws the screen at once, though each of its cores follows one list of instructions at a time. A program called the operating system takes turns among the others so fast that each seems to run alone. It saves and restores their places, chooses who goes next, keeps them from blocking each other forever, and walls each off from the rest. This page builds the turn-taking from 40d’s stack, finds which order of turns makes the average wait least, finds the shape of a deadlock in a graph, and says where the wall stands.

Give each program a short slice of time; on a switch, save its registers and stack pointer and load the next one’s. Shortest job first gives the least average wait, by swapping neighbours. Programs that each hold what the next wants, round a cycle, wait forever; number the resources and take them in order and no cycle can form. Only the operating system may touch the hardware; programs ask it by a call.

40comp21Turns Too Fast to See

Sarah’s laptop has one core and three programs ready. The operating system lets each run for a slice of about 10 milliseconds, then a timer interrupts it and the next takes over.

\text{slice} \approx 10 \text{ ms} @@ a hundred turns a second
3 \text{ programs: each runs } \tfrac13 \text{ of the time} @@ each seems to run, slower
\text{a timer interrupts, whatever the program is doing} @@ no program can keep the chip
\htmlClass{new}{\text{programs waiting on a disk or a key press get no slice}} @@ they are not ready

From here on, on this page, a process is a program while it runs: its instructions, its data, and its place.

40comp22Saving a Program’s Place

40d found that a running program’s place is its registers, its current instruction and the top of its stack. That is all the switch must save.

\text{save registers, instruction pointer, stack pointer} @@ the place, by 40d
\text{load the next process’s saved place} @@ its stack is still in memory
\text{switch} \approx \text{a few microseconds} @@ plus cache misses (39comp)
\htmlClass{new}{\text{the process resumes as if never stopped}} @@ it cannot tell it was paused

Switching technique: a process can be stopped and resumed anywhere by saving its registers and stack pointer, since its stack holds the rest. Slices much shorter than the switch would spend the chip on switching.

40comp23Who Goes Next

Three jobs arrive together, needing 8, 4 and 1 milliseconds. Each waits for the ones run before it.

8, 4, 1:\ \text{waits } 0, 8, 12;\ \text{average } \tfrac{20}{3} \approx 6.7 @@ longest first
1, 4, 8:\ \text{waits } 0, 1, 5;\ \text{average } 2 @@ shortest first
\text{swap neighbours } a > b \text{ run } a, b:\ \text{the wait changes by } b - a < 0 @@ a swap that never hurts
\htmlClass{new}{\text{shortest first gives the least average wait}} @@ swap until sorted

Running the shortest job first makes the average wait least: swapping any longer job ahead of a shorter one only lowers the total. But a job’s length is rarely known in advance, and a long job could wait forever, so real systems guess lengths from the past and age the waiting jobs up. 31·logi’s queues say how long the line grows.

40comp24Waiting Forever

Process A holds the printer and waits for the disk; process B holds the disk and waits for the printer. Neither lets go.

A \to B:\ A \text{ waits for what } B \text{ holds} @@ an arrow of 42a’s dots and links
A \to B \to A @@ a cycle
\text{a cycle} \iff \text{every process in it waits forever} @@ each held resource has one holder
\htmlClass{new}{\text{number the resources; take them only in rising order}} @@ then no cycle can form

If every process takes resources in rising order, an arrow from a holder of resource i points to a holder of some j > i, so a cycle would need the numbers to rise all the way round and come back, which is impossible. Taking shared resources in one fixed order rules out waiting forever.

40comp25A Wall Between Programs

\text{kernel mode: may touch hardware and the address tables} @@ only the operating system
\text{user mode: may not} @@ every other program
\text{to read a file: a call into the kernel} @@ like 40d’s calls, through one guarded door
\htmlClass{new}{\text{each process sees only its own made-up addresses}} @@ 39comp’s tables, set by the kernel

The operating system alone runs in a mode that touches hardware; every other program asks it through a call, and sees only its own memory. A crashed or hostile program then harms only itself, which is why one bad tab need not bring down the phone.

Accepted names

Taking turns by slices is preemptive scheduling, in equal turns round robin; saving and loading a place is a context switch. Shortest first is SJF. Waiting forever is deadlock, drawn as a wait-for graph, and the rising order is lock ordering. The two modes are kernel and user mode, and the guarded door a system call.

Who said it first

Time-sharing ran on MIT’s CTSS in 1961. Edsger Dijkstra posed the dining philosophers in 1965, and Coffman, Elphick and Shoshani set out the conditions for deadlock in 1971.
