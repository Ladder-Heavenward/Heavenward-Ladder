46·crypt · cryptography

How Does a Browser Know It Is Talking to Its Bank?

How does a browser know it is talking to its bank? 43·comp let two strangers agree a secret in public, and 44·crypt found the flaw: a device in the middle can agree one secret with each side and pass messages between them, reading all. Earbuds beat it with a six-digit check read by a person. A browser has no person to ask. The fix is a chain of signatures: the bank signs its half of the exchange, a company the browser already trusts vouches for the bank’s signing key, and the browser checks the chain before sending a byte. This page builds the chain, runs the handshake that sets up every padlocked web page in one round trip, and shows why a stolen key years later cannot open today’s talk.

Plain key exchange is open to a device in the middle. The server signs its half; a certificate binds its name to its signing key, signed by an authority whose key the browser ships with. The browser checks the chain up to a root it holds, then both derive the session keys from the shared secret. Fresh halves every time mean old talk stays locked even if the long-term key leaks.

45crypt1A Stranger in the Middle

Claire’s browser and her bank run 43·comp’s exchange: each picks a secret power and sends g to that power. Mike sits on the café’s wifi.

\text{Claire sends } g^a;\ \text{Mike keeps it, sends } g^m @@ to the bank
\text{bank sends } g^b;\ \text{Mike keeps it, sends } g^m @@ to Claire
\text{Claire shares } g^{am} \text{ with Mike; the bank } g^{bm} @@ two secrets, both his
\htmlClass{new}{\text{the exchange says nothing about who is at the other end}} @@ 44·crypt’s device in the middle

From here on, on this page, to authenticate a message is to give proof of who sent it that no one else could forge.

45crypt2Signing the Half

\text{the bank has a signing key } s \text{ and a checking key } v @@ like 43o’s RSA pair
\text{bank sends } g^b \text{ and } \text{Sig}_s(g^a, g^b) @@ a signature over both halves
\text{Claire checks it with } v @@ only the holder of s could make it
\htmlClass{new}{\text{Mike cannot sign } g^m \text{ as the bank}} @@ his swap is caught

Signed-exchange technique: the server signs the key-exchange messages with a long-term key, so a stranger who swaps in its own half cannot produce a valid signature. But how does Claire know v is the bank’s checking key, and not Mike’s?

45crypt3Who Vouches for the Key

\text{certificate: “} v \text{ belongs to mybank.example”, signed by an authority} @@ a signed statement
\text{the authority’s key, vouched for by a root} @@ one more link
\text{root keys ship with the browser} @@ trusted in advance
\htmlClass{new}{\text{check each signature up the chain to a root}} @@ a path in 42’s graph of who vouches for whom

An authority checks that whoever asks for a certificate really controls the name, often by asking them to put a given word on the site. Trust is carried down a chain of signatures from a few root keys the browser holds. Certificates expire, and a revoked one is listed, because keys get stolen.

45crypt4The Handshake

The current version of the web’s padlock, TLS 1.3 from 2018, does all of this in one round trip.

\text{browser} \to \text{server: } g^a, \text{ ciphers it knows} @@ guessing the server’s group
\text{server} \to \text{browser: } g^b, \text{ certificate chain, signature, check} @@ all but its half locked under keys from the shared secret
\text{both: keys from } g^{ab} \text{ and all messages so far} @@ a fingerprint of the whole talk
\htmlClass{new}{\text{data flows after one round trip}} @@ earlier versions took two

The handshake agrees a fresh secret, proves who the server is, and binds both to a fingerprint of every message exchanged, so no step can be quietly changed. After it, 27·crypt2’s locks with message tags carry the data.

45crypt5Old Talk Stays Locked

a, b \text{ fresh each time, forgotten after} @@ never stored
\text{the long-term key only signs} @@ it never locks the secret
\text{steal it in five years: } g^{ab} \text{ still needs } a \text{ or } b @@ 43·comp’s hard problem
\htmlClass{new}{\text{recorded talk from today stays locked}} @@ the signing key cannot open it

Older versions could lock the session secret under the server’s long-term key, so one stolen key opened years of recorded talk. TLS 1.3 removed that option. Fresh halves forgotten after each talk keep past talk safe even when the long-term key is lost.

45crypt6Moves to Watch Out For

Each line below is a move that looks right and is not. The tag says what kind of mistake it is; the words say which footing catches it.

\text{lock the exchange, then it is safe from Mike}\,? @@ <span class="vd vd-c">outside the collect</span> the exchange itself must be signed, or Mike swaps in his half (45crypt2)

The cellar · there if you want it

Accepted names

The padlock is TLS (Transport Layer Security, successor to SSL); the signed exchange is authenticated key exchange, the attack a man-in-the-middle attack. Certificates follow X.509; the authorities are certificate authorities and the chain a public key infrastructure (PKI). Fresh halves give forward secrecy; the halves are ephemeral Diffie-Hellman keys.

Who said it first

Netscape released SSL 2.0 in 1995; TLS 1.0 followed in 1999, and TLS 1.3 was published as RFC 8446 in August 2018. Diffie and Hellman, who gave the exchange in 1976, already noted that its halves must be authenticated.
